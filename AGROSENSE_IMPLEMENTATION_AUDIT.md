# AgroSense-360 — Stage 14 Implementation Audit

**Audit date:** 2026-11-20  
**Scope:** Current repository source and locally executable checks. This audit does not claim a production or deployed environment.

## Scope and evidence boundaries

- Reviewed the React/Vite application, API client, FastAPI routers and integrations, settings/security, SQLAlchemy models, Alembic chain, dataset governance and training scripts, tests, Docker files, and relevant deployment/demo documentation.
- No `.env` or `.cdsapirc` file was read, printed, or changed. No external API request, dataset download, model training, migration application, or schema change was performed.
- The worktree had pre-existing modifications and untracked files. They were preserved; this stage adds only the three requested audit documents.
- Backend tests ran against the repository's isolated SQLite fixture. Its spatial functions are test stubs, not PostGIS. No Supabase or persistent database connection was attempted under the allowed test setup.
- “Exists in source” is not treated as evidence that a provider, model, deployed database, or production workflow works.

## Tomorrow's smallest honest demonstration

The smallest genuine application workflow supported by the code is a **read-only catalogue lookup with visible verification/provenance status**:

1. Load the public portfolio frontend with `VITE_PUBLIC_DEMO=true`.
2. Confirm the API reports `public_demo_mode: true` and a connected database.
3. Load districts, categories, and crops; search/select a crop; inspect its profile, sources, and verification state.
4. Show blank/pending profile fields and absent district associations as unavailable evidence—not as unsuitable crops or recommendations.

This is a real catalogue retrieval/display workflow, **not an ML prediction, weather forecast, diagnosis, or verified agronomic recommendation**. At the time of this audit, no live database was verified, so it is not yet demonstrated end to end. Without a verified database/API, the only honest fallback is a UI/build walkthrough that explicitly labels the backend as unavailable; do not substitute fixture data or fabricated results.

## Production architecture review

| Capability | Current assessment |
|---|---|
| Modular services | Some separation exists (`agriculture.py`, `integrations.py`, `security.py`), but `main.py` still owns substantial farm CRUD, geometry conversion, and route logic. There is no mature service/repository boundary. Adequate for a compact prototype; extract only where shared behavior or testability justifies it. |
| Secure authentication | Password hashing, signed expiring JWTs, owner-scoped farm queries, explicit CORS, and allowlisted catalog administration are implemented and tested. Production gaps include no rate limiting, recovery/MFA, revocation, or demonstrated operational key rotation; browser tokens use `sessionStorage`. |
| Role-based authorization | Present as an email allowlist for catalog administration. It is not a general role/permission model and has no organization/tenant roles. |
| Dataset provenance | The licensing gate, signed reviews, provenance manifest checks, and checksums are meaningful foundations. Current local ERA5 archives conflict with inventory acquisition metadata, and no durable ingestion registry or end-to-end ingestion is proven. |
| Versioned ML models | Not implemented as a registry or serving lifecycle. Training scripts can write artifacts, but no validated artifact is deployed, loaded, or reported as ready. |
| Provider-independent LLM | Documentation only. There is no provider interface, retrieval service, index, evidence record flow, or citation validation. |
| Background processing | Not implemented. No job queue/worker or persistent job state exists. |
| Logging and monitoring | Minimal framework/health behavior only; structured redacted application logs, metrics, tracing, alerting, and backup/restore evidence are absent. |
| Environment separation | Backend environment settings and public frontend build-time settings exist. Deployment parity and secret handling are documented, not verified in an automated release pipeline. |
| Future scaling | A modular monolith with Postgres/PostGIS is a reasonable foundation. Synchronous SQLAlchemy routes and no worker/observability may constrain heavier ingestion/inference, but there is no evidence that microservices are needed now. |

**Overall conclusion:** the repository contains a tested prototype foundation for authentication, farm/plot APIs, and a provenance-aware public catalogue. It does not establish a working Supabase deployment, live weather/ML/RAG/disease services, or production readiness.
